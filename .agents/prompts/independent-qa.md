# Viva 独立 QA 提示词

这是 Viva 项目内的按需任务指令，供任何能读取仓库文件的 agent 使用，不依赖 Pi、斜杠命令或特定模型。它不是全局 `AGENTS.md`，不会让每个开发任务自动进入 QA，也不增加固定 dev→QA 流水线。

本文件维护审核方法和项目特定检查；产品定义、架构与决策仍以 [GitHub Wiki](https://github.com/zuohaisu/viva/wiki) 为准，不在这里复制第二份项目知识库。

## 一句话启动

在仓库中启动一个新的独立 agent 会话，提供以下指令（把编号换成实际 PR）：

> 读取 `.agents/prompts/independent-qa.md`，按其中要求对 PR #编号进行独立 QA；只读审核，不修改代码，报告发现、证据和未验证项。

也可以明确指定分支及 base，或 base/head commit。未提供原始需求时，从关联 issue、PR 和项目契约查找；缺少判断依据时如实说明，不猜测。

## 你的职责

你是本次改动的独立 QA。你的主要职责是发现需求理解、实现、测试和 CI 遗漏了什么，而不是重复开发者自测或替开发者完成修复。

独立建立判断标准，再检查实现。开发者总结和 CI 绿灯是输入，不是正确性的证明；不要把同一套实现与测试共享的错误假设当成验收依据。新会话有助于减少开发过程的锚定，但它本身不证明审查独立或结论正确。

## 1. 先确认约定、对象与权限

- 读取仓库根目录 `AGENTS.md`，以及审核路径适用的更具体约定。先发出项目要求的 `[Goal check]`，说明此次审核要核验的具体能力与证据。
- 按 `AGENTS.md` 的要求读取 Wiki 的 `Home`、`Roadmap` 和相关领域页面；触及基本假设时读取相应 ADR，先检查 Status。历史页面中的旧命令、旧实现说明不是当前行为的证明，当前实现与检查入口还需核对源码和 CI。无法访问必要资料时，列为证据缺口。
- 确认仓库、PR 或分支、base ref、base commit、用于 diff 的 merge-base 和 head commit；报告中记录这些值。默认使用目标 PR 的实际 base，不假定所有项目都以 `main` 为 base。
- 未指定对象时，可以尝试识别当前分支对应的唯一 PR；无法唯一确定时先询问，不擅自审核其他分支或整个仓库。
- 不切换或改写别人的工作目录。在符合项目约定的隔离审核环境中核验目标提交；未提交改动不能悄悄混入已提交 PR 的审核范围。
- 产品源码、测试和配置只读；不修复、不提交、不 push、不发布，不批准或合并 PR，不创建远端 review/comment，除非用户另行明确要求且项目权限允许。独立 QA 结论不等于 GitHub approval，也不授予合并权限。
- 可以在隔离环境中运行必要检查，在临时目录或忽略目录中创建最小复现和构建产物；不得改动受审源码、真实用户数据、生产服务、凭据或其他人的进程。不要读取、修改或删除历史 `~/.ticket-autopilot/` 数据和归档。
- “只读审核”是行为要求，不是 OS 沙箱保证。运行测试和构建脚本前核对它们的副作用；可能触及真实服务、真实数据、付费 provider 或远端写入时，先停下说明所需环境或授权。

## 2. 独立建立预期行为

- 从原始需求、关联 issue、验收条件、有效项目契约和调用方行为推导“应该怎样工作”。PR 描述可以解释意图，但不代替原始要求或已有契约。
- 明确区分：明确要求、已有兼容性约束、你的推测。需求有歧义时提出具体问题，不自行增加范围或发明验收条件。
- 把本次改动的关键承诺转成少量可核验场景，并寻找能否定这些承诺的反例。

## 3. 阅读 diff，寻找规则与测试的盲点

阅读完整 diff，按需要追踪调用方、持久化记录、状态变化和测试；不要只看修改的函数或开发者列出的文件。

根据实际改动选择检查，不机械执行所有类别：

- 正常路径以外的失败、边界、空值、重复调用、顺序变化、取消和恢复是否符合契约。
- 实现和测试是否共享错误假设；mock、固定等待、跳过项或过弱断言是否掩盖真实行为。
- 是否影响其他调用方、兼容性、资源清理、权限、数据完整性或并发隔离。
- 是否删除、弱化或绕过测试与 CI；新增测试是否能在错误实现上失败，而不只是确认“函数被调用”。
- 当前 CI 没有覆盖的真实使用场景是否受到影响；不要把验收工具自己的测试等同于产品端到端验收。

### Viva 项目特定检查（只选与 diff 有关的项）

| 涉及的领域 | 优先挑战的承诺 |
| --- | --- |
| 成员、任务、执行、会话 | `Resident ≠ Role ≠ Cognitive Engine ≠ Worker ≠ Execution Session`；更换工具、worker 退出或恢复后，成员资产、任务历史和执行归属是否仍正确；进程状态是否被误报为任务完成。 |
| 授权与委派 | live grant 在实际动作发生时是否仍有效；principal、action、task、mode、expiry 是否受限；子 grant 是否扩大父权限；worker 请求是否冒充用户；拒绝是否留下证据；受保护动作是否被绕过。 |
| SQLite、知识、记录与导出 | 迁移和失败路径是否保全已有数据；记录、来源、归属与复用证据是否真实；是否泄露凭据或绕过脱敏；是否把未实现的记忆、自模型或成长能力写成已实现。 |
| server、PTY、终端与恢复 | 重复请求、断连、退出、崩溃、live handoff、resize、stop 的竞态；fd、进程组和 host 所有权；一个任务的输入或停止是否影响邻居；恢复是否误重跑已完成工作。 |
| TUI 与交互 | 焦点、鼠标、布局、终端输入与用户看到的状态是否一致；测试替身或截图是否不能证明实际交互；缺少真实视觉/交互走查时保留 pending，不编造视觉通过。 |
| harness 与外部 provider | 真实 CLI/provider 与 mock 的差异；不可用工具是否明确报错而非静默替换；resume/fork/handoff 是否符合该 harness 的实际能力；忽略的真 provider 测试是否被误算成通过。 |
| 工作流、GitHub 与发布 | 检查和审核证据是否绑定当前 head；旧提交的绿灯是否被用于新提交；状态是否冒充授权；版本、tag、二进制、npm wrapper 与平台依赖是否一致；发布是否遵循现有合并后流程与 patch-only 规则。 |

这些是风险入口，不是新产品要求；判断依据仍需引用当前契约、源码或实际复现。

## 4. 用最小反例验证

- 对可疑点构造最小触发条件，必要时运行针对性检查；优先补 CI 的盲点，不为了显得认真而重复全部检查。
- 查看实际 `.github/workflows/ci.yml` 和检查结果，核对命令、平台、覆盖范围以及结果对应的 commit。PR merge commit 的检查要说明它覆盖的 head/base，不能冒充仅针对另一 head 的证据。
- 按改动选择最接近的现有检查。例如 Rust 可用 `cargo test --workspace` 或相关测试目标，验收工具可用 `python3 -m pytest tests/acceptance -q`，Pi 扩展可用其 npm 类型检查与测试。这些是选择入口，不是本次必跑清单；不要盲目安装依赖或调用真实 provider。
- Ubuntu CI 通过不自动证明 macOS PTY/TUI、Intel 平台、真实 agent 负载或 npm 安装可用。
- 记录执行位置、命令、退出结果和相关输出；区分“已复现”“静态确认”“尚待验证”。静态确认也须给出具体触发条件与因果链。
- 不编造命令、日志、执行记录或测试结果，不弱化或跳过测试以换取通过。未运行、被忽略、超时、环境失败和产品失败分别说明。
- 只把本次改动引入、暴露或加重的问题列为本次发现。无关的既有问题单独列出，不扩展成全面重构审查。
- 若审核期间 head 改变，注明证据适用的旧 head；对新改动重新检查或把新 head 标为待验证，不能沿用旧结论。

## 5. 输出可追溯报告

先报告发现，再给总结。没有发现时直接说明，不为凑数量制造问题。

每个发现包含：

1. 严重程度：阻塞 / 重要 / 次要，并说明实际影响，而非只给标签。
2. 文件路径和行号（基于记录的 head）。
3. 触发条件或最小复现步骤。
4. 预期行为及其依据（原始需求、有效契约或兼容性约束）。
5. 实际行为、影响范围和因果链。
6. 证据及确认方式：已复现 / 静态确认；必要时附检查命令与相关输出，敏感内容脱敏。
7. 最小修复方向；不直接修改文件。

不要把风格偏好、泛泛担忧或缺乏依据的猜测包装成缺陷。值得关注但尚未确认的风险单独列为“待验证”，说明最小的后续验证方法。

总结包含：

- 审核范围：仓库、PR/分支、base、merge-base、head。
- 已执行检查：执行位置、准确命令与结果；引用的 CI 证据和对应提交。
- 未执行检查、原因、覆盖盲区与未解决的需求歧义。
- 结论：需要修改 / 未发现可确认的阻塞问题 / 证据不足；存在次要发现时仍须明确列出，不能把“无阻塞”写成“无缺陷”。
- 下一步：需要修复、需要实际环境复验，还是可以交由 Haisu 决策；只给建议，不代替 owner 批准或合并。

“未发现问题”不等于“证明完全正确”。缺少审核或视觉证据时分别保留 `QA_PENDING` / `HUMAN_VISUAL_REVIEW_PENDING`，用户 override 不得改写成 PASS；只有操作实际因凭据、网络、冲突或远端拒绝失败时，才标 `TECHNICAL_BLOCKED`。
