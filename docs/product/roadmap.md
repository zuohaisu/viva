# Viva Roadmap — 从可用工作台到持续协作的 AI 成员

Status: **Proposed / 待 Haisu 评审** · 基线：2026-10-06，`origin/main` commit `7fc51b3`。

本文是产品路线建议，不是新 ADR、实现承诺或验收 PASS。现行宪章及 accepted ADR 继续约束实施；阶段编号不对应 npm minor 版本。产品北极星见 [vision.md](vision.md)，技术边界见 [ADR 0011](../decisions/0011-rust-host-and-tui.md) 与 [ADR 0012](../decisions/0012-resident-runtime-and-terminal-orchestration.md)。

## 1. 终局：不是复刻终端工具，而是让协作产生复利

> Haisu 从任何受支持的工作入口找到同一批长期成员；成员能换模型、换工具、换会话继续任务，在授权范围内组织其他成员，并把有来源的工作经验用于后续工作。

衡量路线的四个问题：

1. **能工作吗？** 不依赖 Orca，从普通终端完成真实并行任务。
2. **能接着工作吗？** 会话结束或模型更换后，目标、决定、未完成项和必要知识不蒸发。
3. **能组织工作吗？** 一个协调成员受控分派、跟进、交接、核验证据，而非仅向几个窗口输入文字。
4. **积累能保全吗？** 成员资产可导出、恢复，最终可跨设备使用，不绑定供应商或某一进程。

Herdr 提供运行时参照，Orca 提供工作台体验参照；二者不是 Viva 的终局。记忆不是全量日志，自模型不是人格提示词，编排不是固定 Dev→QA 流水线。

### 文档漂移的处理

`phase-1.md`、`vision.md`、ADR 0012 的 implementation 行及早期规划有“未实现”旧标记，而后续代码已经存在。本文据代码、测试、合入记录与发布记录确定实现基线；**不改写历史验收结论**。关闭界面默认继续、显式 pause、server 持有 PTY 的语义以 ADR 0012 为准，不沿用首版文档中的“关 TUI 即停止”。

[V12 记录](../validation/v12-final-acceptance.md)仍明确：三真实任务（Pi + 第二 CLI）、Intel Mac、16 真实 Agent 负载等 pending。旧 sleep/PTY 数据不能代替升级后运行时的真实 Agent 验收。[F01–F04 记录](../validation/f01-f04-acceptance.md)的待独立复验及限制也不能因工单关闭被抹掉。

## 3. 推荐顺序：四个主里程碑，一条证据驱动的研究线

```text
M1 日常主力终端工作台
          ↓
M2 单机成员连续性与可用记忆
          ↓
M3 有边界的 Agent 编排与协作闭环
          ↓
M4 可携带资产、跨设备同步与 SSH 工作面

研究线：M1 定 self-model 边界 → M2 积累候选 → M3 用真实行为检验 → 后续受控演化
```

相对初步四期构想的调整：

- **合并 Herdr 与 Orca 到 M1**：运行时和工作台是一件事的两面。基础大多已建，下一步应收口可用性，不再建设第二套平台。
- **连续性从 M1 就留接口，M2 做实**：不等终端功能无限完善才开始积累工作资产。
- **单机记忆与跨设备同步拆开**：跨 session/模型/harness 不要求云；同步正确也不证明召回正确。
- **编排先于多设备同步**：本机已具备编排原语，先让它产生实用价值；云运维不应成为协作的前置条件。
- **Self-Model 从第一期确定关系，晚些验证演化**：没有跨情境行为证据，就不先造“成长引擎”。

阶段是验收门，不是长时间封闭开发。每期按独立 worktree/PR 交付小闭环；已有能力不重做。SSH 是 ADR 0012 已接受的后续目标，本建议只安排先后，不取消它。

## 4. M1 — 成为每天可用的主力工作台

**用户承诺：** 只开 Viva，就能在多个项目中并行工作、查看改动、人工交接、断开重连，并清楚知道谁在做什么。

重点收口：

- 处理 #63 的 fd 生命周期疑点，复验 detach、输入/resize、stop、live handoff 的竞态；不通过放宽断言掩盖产品故障。
- 走查已建 V14/V15：项目→任务→worktree→Agent/测试/shell→diff/PR→handoff→恢复；补最影响日常操作的缺口，而非追求所有 Herdr/Orca 功能对等。
- 建立 harness 能力矩阵：可启动、可交互、可报告状态、可交接、原生 resume、原生 fork，各自注明 tested/unsupported/unknown。七种 CLI“可识别”不等于七种都完成深度集成；启动提示、文档和实际 provider 状态也需一致（当前 Pi 入口已注册 memory tools，却仍有“未连接记忆”的固定提示）。
- 审计 socket 调用来源、终端目标范围与取材脱敏。当前 same-UID owner 路径不是 OS 沙箱；成员身份字段和提示词也不是防恶意进程的认证边界。
- 每次结束/交接保留结构化工作包最小字段：成员/Task/Execution 引用、目标、约束、关键决定、未完成项、代码/产物版本、原始材料引用。复用 Task brief，不另建会话事实库。
- 定下 §8 的 self-model 边界，只实现确有需要的证据契约，不引入兄弟仓库运行依赖。

**退出门：**

1. Orca 不运行、不调用其 CLI；在真实低风险仓库同时完成至少 3 个任务、3 个 worktree，包含 Pi + 第二种真实 Agent CLI，以及测试/shell 终端。
2. 人工输入/路径/结果不串；stop 一个不影响其他；detach 后继续、attach 可找回；显式 shutdown 回收 owned 进程且保留改动。
3. 真实 diff、测试、独立 review、必要 PR 均能关联正确 head；Agent 不自行 approve/merge。
4. 建议完成连续 5 个工作日试用，记录被迫退回 Orca 的具体原因与阻断问题；这是新建议的用户验收，不是现有 PASS。
5. 目标平台/负载预算先写明再测；Intel 与 16 真实 Agent 门槛未满足则保留 pending，不用 Apple Silicon 或替身数据代替。

**不阻塞核心收口的长尾：** 主题、国际化、音效等按 #49 跟踪；不另做 IDE、插件市场或桌面客户端。

## 5. M2 — 同一成员换会话、模型、工具仍能接着做

**用户承诺：** 昨天的有效决定与未完成工作，今天不必重新解释；能追问依据、修正过期知识，成员间共享不会污染私人资产。

先澄清“跨 Agent”：

- **同一 Resident 换模型/harness/Worker**：延续同一资产与任务，不承诺行为完全一致或原生上下文无损。
- **不同 Resident 协作**：共享项目/团队知识、明确交接材料；不是复制所有人的私人记忆，也不是变成同一个成员。

交付三个闭环：

1. **Resume packet**：复用 Task brief + 知识选择 + 原生会话引用，启动时装配有预算的工作包。动态事实（授权、Task 状态、HEAD）查询当前来源，不能从旧摘要恢复成权威事实。
2. **Recall → 使用 → 修正**：先比较现有 Holographic、文件/SQLite 入口与仓库已有 OpenViking 候选研究；用相同材料、回答模型和上下文预算做中文、时效、冲突、隔离测试，再决定后端。先复用，不自研向量库或 token manager。
3. **候选 → 策展 → 生命周期**：摘要只提出候选；保留来源与事实/推断区分，支持 supersede/archive/restore。读取、注入、成员声明使用、效果验证分别记证据；现有 `memory_usages` 记录搜索返回，不能直接升级为“成功复用”。

现有 `knowledge` 与 `memory` 不再平行写同一正文：前者治理归属/来源/生命周期，后者或普通文件持有指定正文，只有一个权威来源。共享层复用 project/team/skill 语义；当前 Holographic 的个人 link 过滤不是完整团队共享机制。若需统一受控读写入口，优先扩展既有 Viva 服务与薄适配，不再起一套独立 Agent 平台。

**退出门：**

- 同一成员做三次真实执行：新 session → 换模型 → 换 harness；仍能找到有效约束、未完成项和原始来源。至少两种模型、两种 harness。
- 预先冻结一组真实问题：中文改写、低频重要决定、新旧事实冲突、未知问题、同名项目、跨成员隔离；对比“无记忆 / 当前适配 / 候选改进”，分别报告召回、最终答案、过期误答、来源与 token/延迟，不只报告存了多少条。
- 关键有效约束不靠 top-k 碰运气；测试中私人内容零跨成员泄漏，过期事实不冒充当前事实；质量门槛在实验前固定。
- 第二个成员仅通过项目/团队范围复用真实条目并留下 execution 级证据；归档后退出默认召回，历史仍能回查。
- Provider 不可用时明确显示 degraded/unavailable，不静默换后端、不伪造记忆。

**不做：** 云同步前置、全量 transcript 自动晋升、自动身份改写、所有 harness 原生会话格式互转。

## 6. M3 — 一个协调成员能组织多个成员完成工作

**用户承诺：** Haisu 批准目标、范围与预算后，一个协调成员能组织执行、核验证据、失败交接并请人决策，而不是 Haisu 持续搬运上下文。

分两步，不等 M4：

- **M3a 受控委派**：复用现有 dispatch/status/result/stop、prompt/wait/events、F01 workflow；先跑可解释的小闭环。M1 稳定后可与 M2 并行试验，不要求“完美长期记忆”。
- **M3b 可恢复协作**：依据真实阻断补最小依赖/预算/协调状态；Coordinator session 死亡后，新执行从 Task/Execution 与证据继续，不靠聊天记录猜阶段。

新增调度只负责执行已批准的计划和证据条件，不再维护一套竞争性的 Task 状态，不重启退役 ticket pipeline。模型负责提议；确定性控制面负责授权、幂等、预算和留痕。

**必须先解决的边界：**

- ADR 0007 的子 grant 不得扩大，Task 范围不能由协调成员自行扩展。跨多个独立 Task，先由 Haisu 批准清单并逐 Task 授权；不能拿 Task A 的 grant 调度 Task B。若未来需要任务组委派，另立 ADR，不暗改规则。
- 写入任务默认独立 worktree，避免两个开发执行无协调地改同一树。Reviewer 是独立执行/成员，结论绑定真实产物版本。
- 首版限制执行数、调用/费用、总时间、重试次数；限额、无证据、依赖失败时暂停或升级给人，禁止无限互调。
- 受控状态是“成员报告”，仍需测试/产物证据才算完成；屏幕文字、安静窗口、exit 0 都不是验收 PASS。
- 重要外部写入、worktree 删除与交付仍遵守 owner 授权；开发/QA 成员不自批自合并。已有 helper 或同 UID shell 能力不等于安全隔离证明。

**退出门：** 至少两种真实协作形态（如并行研究汇总、开发+独立复核），协调成员组织 ≥2 个执行成员；人为制造一次失败、一次协调会话中断、一次撤权，分别证明有界交接、无完成任务重放、撤权后拒绝。每个结果有 actor、Task、Execution、模型/工具、授权、产物版本及证据引用；未通过项如实保留。

## 7. M4 — 可携带资产、跨设备同步与远程工作面

**用户承诺：** 换电脑不会丢成员资产；离线能工作，恢复同步不会静默覆盖决定；远程机器上的执行仍能明确归属。

### 7.1 服务端和文件夹不是同一个问题的二选一

| 问题 | 推荐 |
| --- | --- |
| 一台机器，多 session/模型/harness | 同一个本机 Viva 控制面与记忆入口；无需外网同步 |
| 两台机器偶尔切换、主要单写 | 本机状态 + 显式导出/导入的加密资产包；云盘仅搬运不可变包 |
| 两台机器经常并发写、需低延迟 | 再评估成熟同步/自托管服务，通过对象级协议合并；仍保留离线副本 |
| 远端 Agent 执行与观察 | SSH driver/远端 Viva，独立于记忆同步；不是把远程执行状态当本地状态复制 |

**建议首选混合方案：本机为主，开放格式为资产边界，传输后端可替换。** 学习 KeePassXC 的本地所有权、可携带与加密思路，不照搬“一个文件等于整个协作运行时”。AI 资产包含正文、来源、归属、版本与引用，且多 Agent 并发写入，不能只同步 `memory.md`。

### 7.2 百度网盘可以做什么，不能做什么

可以作为加密备份/资产包的运输方式，前提是后续验证实际客户端的完整上传、下载、冲突文件与延迟行为；本文没有测试百度网盘、KeePassXC 或给出其产品级能力保证。

**不要把运行中的 `VIVA_HOME`、`office.db` 或 Holographic DB 放进同步目录让两台机器共同打开。** SQLite/WAL 的锁与事务不是云盘冲突协议；即使能完整复制，两个设备上的独立新写入也不会自动得到正确合并。

第一版只支持**明确交接的单写工作模式**：停止旧写入→一致性快照→上传完整包→新设备验证并导入。云盘文件锁不能被宣称为可靠的分布式锁；检测到代际不匹配或两端都有新写入就拒绝覆盖，进入人工冲突处理。不可变包写临时名，完成后发布 manifest；接收端验证所有对象后才事务性采纳。

### 7.3 同步资产，不同步“活着的进程”

候选可携带范围：成员配置版本、已策展知识/技能、批准的自模型假设、交接包、选定历史证据与来源引用。凭证、活跃 socket、PID、PTY、文件锁与本机路径不作为可恢复执行同步；grant 可作为历史证据，但导入不使它在另一设备自动获得执行效力。

必须补的最小语义：

- 稳定资产 ID、对象版本、来源设备、替代/归档事件；provider 的本地整数 `fact_id` 不是跨设备稳定身份，需受控映射。
- 正文与元数据一同保全；跨设备路径做显式重绑定，摘要不能取代缺失原始证据。
- 先复用 SQLite backup/成熟快照、现有 export、文件与成熟加密工具；现有 `data export` 不是完整记忆备份或导入产品，外部 provider 与文件材料需另纳入一致性清单。
- 私有权限不等于加密。上传前本地加密，密钥不跟包同传；复用成熟认证加密，不自造密码协议。泄露、密钥丢失、恢复演练都要有方案。
- 冲突不按“最新时间戳获胜”静默合并；保留双方版本、归档/撤回意图与决策理由。导入材料是数据，不是可自动执行的提示词、技能或授权。
- 同步协议与存储传输分离：手工移动先跑通，再接云盘；并发需求真实出现再引入多写服务。新传输/服务选择需单独裁决，不在本文批准。

**退出门：** 先在两台真实设备验单写交接→导入→重建索引→查询原始来源；再故意让两端离线产生新写入，证明识别冲突并进入人工采纳，而非宣称已支持自动多写。覆盖重复、冲突、已归档知识、中断上传包与过期快照；无静默覆盖、无归档复活、无权限扩张。另演练从备份恢复。SSH 执行保留远端归属、断连事实与授权边界，不冒充本机恢复。

## 8. Viva 与 self-model 的架构关系

这里将用户的“self-mode”理解为已有 `self-model` 研究仓库；本次只核查 Viva 的[关系研究记录](../research/self-model-relationship.md)，未核查兄弟仓库当前 HEAD。

```text
self-model 研究仓库
  定义概念、假设结构、反思/更新治理原则
         │ 文档参考，不是运行时依赖
         ▼
Viva 产品
  成员/Task/Execution/授权/来源事实
         │ 受控、脱敏、可追溯的材料入口（已有雏形）
         ▼
可选的成员连续性/自模型组件（待实现，先在 Viva 内做最小契约）
  memory 候选 ≠ self-model 假设 ≠ identity 承诺
  提议 → 证据检查 → 人可见的治理 → 版本化状态
         │ 获准材料与状态引用，不得创造或扩大 grant
         ▼
当前 harness + 当前模型（可替换）
         │ 真实行为与反例形成新证据
         └──────────────────────────→ 下一轮检验
```

所有权分开：

| 层 | 拥有什么 | 不拥有什么 |
| --- | --- | --- |
| Viva | 长期成员标识、工作事实、授权、知识归属与生命周期、受控材料通道 | 证明“意识/完整 Self 连续性”、模型内部认知循环 |
| memory provider / 文件正文 | 被指定为权威来源的知识正文与检索能力 | Viva 成员身份与授权、自模型状态的静默改写 |
| self-model 组件 | 有证据的版本化假设、反例、待复审项 | Task 是否完成、owner 权限、模型供应商会话 |
| harness/模型 | 当前会话、工具循环、模型消息和原生 resume/fork 能力 | 成员长期资产的唯一副本 |
| self-model 研究仓库 | 理论与实验分析 | Viva 的运行时安装依赖 |

**按阶段做：** M1 明确材料与假设契约；M2 人可见地积累浅层观察/模式候选；M3 将假设与后续真实行为、反例对照；只有证明它改善协作且能被纠错，才提出自动反思与受控演化的新里程碑。

最小候选需要 proposition、状态、支持/反对证据、产生它的成员与模型/工具、适用范围、版本及 supersedes。换模型前后的表现要区分“成员跨情境模式”与“模型/工具特性”，不能把某次模型表现永久写成成员人格。identity 承诺和用户明确约束不得因一次推断自动改写。

第一期**不**抽共享 Soul SDK、不把三个仓库合并、不启动独立自模型服务；只有第二个真实产品需要相同可执行契约时再评估抽取。Self-Model 对规划与上下文可给建议，对授权永远无裁决权。
