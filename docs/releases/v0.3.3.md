# Viva v0.3.3

## Changed

- `viva update` completes the upgrade by itself: after installing, a
  **running resident server is restarted through the S3 live handoff** —
  the freshly installed entry point takes over as the host and its
  terminals survive. No more manual `viva server-restart` after every
  upgrade; reconnect the TUI when the output asks for it.
- With no server running, the update says so and the next `viva` start
  simply uses the new version. A socket nobody answers is left untouched
  with an honest note — the next start claims it with a recovery record,
  as before.
- A failed handover never fails the install (which already succeeded): the
  old generation keeps serving and the output names `viva server-restart`
  as the retry.
- New flag `--no-restart` restores the old split (install now, restart
  explicitly later).

## Safety and limitations

- The restart step reuses the existing grant-gated handoff protocol; the
  update command itself remains user-only (member/worker contexts are
  still rejected) and never opens VIVA_HOME data or touches member/task/
  history records.
- The resumed host is spawned detached (own process group, output in
  `server.log`), exactly like `viva server-restart` spawns it today; the
  only difference is the entry point: the freshly installed wrapper or
  binary instead of the updating process's old executable.
- npm upload acceptance or a green workflow alone is still not proof of a
  usable release — verify `viva --version` after installing.
